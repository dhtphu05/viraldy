Audit date: 2026-11-24 (Asia/Ho_Chi_Minh). Scope: repository implementation at HEAD `b68d34dc60c076a33ef3f9718b89e60d64047f39` plus the pre-existing working tree. This is a source audit, not a penetration test or a deployment certification. No provider jobs, real credentials, private media, or production infrastructure were accessed.

Scope update: source continued changing during final verification, including unfinished Kie/frontend/config/test work. Findings and line citations refer to the inspected paths and are not a security assessment of later provider adapters. See [the source-drift boundary](VIRALDY_CURRENT_STATE_AUDIT.md#concurrent-source-changes-during-final-verification); no concurrent source edits were authored or reverted by this audit.

**Status vocabulary:** “implemented” means executable source exists, not that it is deployed; “WIP” marks pre-existing modified/untracked scene-repair code; “UI/mock” means presentation or fixture behavior; “missing” means no enforcement was found on the inspected Smart Remake path. WIP repair storage, migration, routes, and screens must not be reported as released production capability.

GitNexus concept search was used for navigation. Its index is ten commits behind the audited HEAD and predates important WIP code. `explain` reported **no taint layer**; an empty finding list therefore supplies no evidence of safety. Conclusions below use current source. The audit changed documentation only, so symbol impact analysis and commit-time change detection were not applicable; no commit was made.

## 1. Assessment

The API has a real authentication and workspace-permission boundary. The WIP scene-repair path adds server-owned object keys, workspace-scoped project lookup, technical checks, revision checks, and idempotent repair operations. Those are useful foundations.

Smart Remake does **not yet have an end-to-end private, rights-cleared, human-approved release boundary**. Its engine still saves an independently downloadable final video through public R2-style URLs or unauthenticated local static hosting. The WIP repair path adds private storage, but does not remove that engine publication path. Source rights, soundtrack clearance, human likeness consent, and AI-content disclosure are not required by the Smart Remake compile/render API. Technical readiness and seller review must not be presented as rights approval or publishing permission.

Priorities below are implementation priorities, not CVSS scores. No cross-tenant exploit or deployed data exposure was executed or claimed.

## 4. Prioritized findings and acceptance criteria

### SR-01 — P0: One private release boundary is not yet authoritative

The engine's [`_finalize_and_save_output`](../../apps/backend/src/viraldy/modules/smart_remake/engine/render_orchestrator.py#L515) invokes capture and then unconditionally calls `save_smart_remake_output`. The synchronous capture callback only appends bytes; the engine saves its legacy public-style artifact before the awaited WIP final callback runs technical assembly checks. See the Unifically branch at [`_render_with_unifically`](../../apps/backend/src/viraldy/modules/smart_remake/engine/render_orchestrator.py#L448). WIP subsequently retains final bytes in private S3, but this does not retract the independently saved legacy copy. R2 errors automatically fall back to local serving; the static route has no workspace/auth dependency. A technically completed generation therefore need not pass a final human/rights release decision before a downloadable copy exists.

**Consequence:** protected API routes and signed WIP URLs alone do not establish private delivery. Anyone who receives a legacy URL can potentially fetch that copy where the configured server/bucket exposes it. Guessability, deployed ACLs, and live reachability were not tested.

**Minimum V2 change:** make a private workspace-owned artifact the only canonical output; use explicit export/release endpoints to issue short-lived downloads after policy checks. Do not silently downgrade privacy when storage fails.

**Acceptance:** unauthenticated and wrong-workspace requests cannot retrieve the output; no legacy public/static duplicate is created; storage failure fails closed; approved export is tied to exact artifact hash/revision; revocation prevents new signed URLs. Verify caches and previously issued URLs according to the documented expiry behavior.

### SR-02 — P0: Rights and consent are not prerequisites for Smart Remake processing

Compile accepts uploaded reference/product media or a product link; render accepts client-returned compile JSON. Neither request requires source asset version, evidence of permission, character consent, reuse purpose, soundtrack clearance, or consent to provider transmission. ProductLock describes product appearance and usage, not rights. The music prompt can select extraction automatically, and [`mux_reference_music`](../../apps/backend/src/viraldy/modules/smart_remake/engine/audio_assets.py#L40) reuses the extracted audio.

A separate general-generation route already calls [`ensure_generation_rights`](../../apps/backend/src/viraldy/modules/generation/service.py#L341) using a self-attested `rights_confirmed` flag. That is a reusable pattern, **not** enforcement on Smart Remake, and a boolean alone does not establish a registry of grants.

**Minimum V2 change:** bind source/product/character/audio asset versions to a rights record with allowed operations and intended uses; block uncleared third-party transmission/reuse where the product policy requires it. Distinguish an uploaded image of a product from permission to copy people, voice, music, brand assets, or advertising claims.

**Acceptance:** missing/expired/revoked grants prevent the relevant compile/render/export operation in backend tests; intended channel and use are checked; every copied audio asset has clearance; reviewer sees unknown rights explicitly; rights and consent evidence are versioned and auditable without placing sensitive evidence in public responses.

### SR-03 — P0: WIP scene-repair lifecycle is not integrated with deletion

The WIP [`SmartRemakeProjectModel.workspace_id`](../../apps/backend/src/viraldy/modules/smart_remake/models.py#L19) references workspaces without cascading deletion. [`DELETION_ORDER`](../../apps/backend/src/viraldy/modules/deletion/policy.py#L17) omits Smart Remake project/operation tables, while [`DeletionRepository.execute_plan`](../../apps/backend/src/viraldy/modules/deletion/repository.py#L139) deletes only that explicit order. [`DeletionResourceType`](../../apps/backend/src/viraldy/modules/deletion/contracts.py#L11) has no Smart Remake project type. Static analysis therefore indicates workspace deletion can fail on the new FK when retained projects exist; this was not executed against a database during this audit.

Existing [`DeletionService.delete`](../../apps/backend/src/viraldy/modules/deletion/service.py#L51) is a good reusable foundation: workspace deletion enumerates `workspaces/{workspace_id}/` objects, queues durable storage cleanup, and retries failures through [`process_pending_storage_deletions`](../../apps/backend/src/viraldy/modules/deletion/storage_cleanup.py#L146). That prefix sweep would cover WIP retained media if database deletion completed. It does not enumerate separate public engine R2 keys, local runtime assets, or provider copies. The generic storage-key extractor recognizes snake_case fields, not WIP `productKey`, `musicKey`, `storageKey`, and `finalStorageKey`; add explicit Smart Remake enumeration for project-scoped deletion.

**Acceptance:** delete a workspace containing Smart Remake projects/operations/versions without FK failure; delete one project and all exclusively owned product/audio/scene/final objects while preserving other projects; retry object deletion safely; confirm removed media cannot be reissued; document provider-side deletion/retention limitations. Test partial storage failure and audit completion.

### SR-04 — P0: Human scene acceptance is not a final release approval

WIP acceptance rejects stale revisions/candidates and failed technical checks. [`technical_check`](../../apps/backend/src/viraldy/modules/smart_remake/repair_media.py#L24) covers probe readability/video-stream metadata, aspect ratio, duration, and optional audio presence. Its probe uses ffprobe stream/format metadata rather than full frame decoding: [`probe_media_bytes`](../../apps/backend/src/viraldy/modules/smart_remake/engine/media_probe.py#L10). It does not establish product fidelity, character consent, claim accuracy, music clearance, or disclosure. Project state contains readiness/revision data but no required reviewer identity, approval scope, rights version, approval timestamp, or final media hash binding. [`present`](../../apps/backend/src/viraldy/modules/smart_remake/repair_service.py#L168) issues a download URL through read access; this does not require the distinct `DATA_EXPORT` permission used elsewhere.

**Priority boundary:** the minimum enforced final approval/export gate is P0 alongside SR-01/SR-02; richer review and comparison tooling can follow at P1.

**Acceptance:** reviewer action is recorded against exact artifact hash and constraint/rights versions; content unknowns remain visible; editing invalidates prior release approval; role policy distinguishes generation, scene selection, release, and export; direct API access cannot bypass the release decision. If viewing includes downloading by product design, document that permission explicitly rather than claiming a separate export restriction.

### SR-05 — P1: Media-download and temporary-asset trust are wider than project authorization

Product-link fetching has explicit public-URL defenses. Provider output fetching does not use that validator: [`UnificallyClient.download_file`](../../apps/backend/src/viraldy/modules/smart_remake/engine/unifically_client.py#L86) follows redirects and buffers the response without a byte cap; [`_fetch_scene_video_bytes`](../../apps/backend/src/viraldy/modules/smart_remake/engine/concat.py#L20) accepts HTTP(S), `file://`, or a bare local path from provider scene records. This makes provider responses and FlowKit a privileged trust boundary. The source audit did not establish a user-controlled path to arbitrary URLs/local files, so it does **not** establish an exploitable SSRF or file-read vulnerability.

Client-returned compile JSON also carries global temporary asset IDs. Audio mux, WIP soundtrack retention, and [`cleanup_render_assets`](../../apps/backend/src/viraldy/modules/smart_remake/engine/asset_cleanup.py#L49) use these IDs with syntax/path checks but no workspace/project ownership lookup. UUID-like IDs reduce guessability, not ownership risk; possession of another valid ID was not obtained or tested. Source-frame IDs are currently used by cleanup rather than a live generation loader.

**Acceptance:** allowlist provider download hosts and redirects or use controlled media ingress; cap response bytes and decode duration; restrict local reads to a managed output directory; bind temporary assets to a compile/project/workspace record and authorize their consumption/deletion server-side. Tests reject private-address redirects, oversized output, out-of-root paths, and another workspace's known temporary asset ID without issuing real provider requests.

### SR-06 — P1: Cleanup is opportunistic and not a complete retention/deletion guarantee

[`cleanup_smart_remake_assets`](../../apps/backend/src/viraldy/modules/smart_remake/engine/asset_cleanup.py#L14) defaults to 24-hour age cleanup; local final cleanup defaults to seven days. Compile/render invoke these sweeps, and render's `finally` removes referenced temporary frames/audio: [`render_smart_remake`](../../apps/backend/src/viraldy/modules/smart_remake/engine/render_orchestrator.py#L157). No scheduled caller was found for these specific cleanup functions. An idle service does not run their sweeps. [`cleanup_stale_smart_remake_outputs`](../../apps/backend/src/viraldy/modules/smart_remake/engine/asset_cleanup.py#L35) explicitly leaves R2 outputs untouched. WIP versions and repeated assemblies create persistent objects without project-level retention/deletion handling.

**Acceptance:** scheduled cleanup records success/failure and backlog; temporary media has an owner and expiry; retained outputs have a stated retention rule; deletion spans all canonical copies; failure does not silently claim erasure. Preserve approved versions according to policy rather than deleting them through a global age-only sweep.

### SR-07 — P1: Error details may return provider metadata and media URLs to clients

Smart Remake [`_error`](../../apps/backend/src/viraldy/modules/smart_remake/service.py#L64) copies engine details into `AppError`; [`app_error_handler`](../../apps/backend/src/viraldy/api/middleware/errors.py#L19) returns those details unchanged. Examples include provider raw errors in [`_response_payload`](../../apps/backend/src/viraldy/modules/smart_remake/engine/unifically_client.py#L139), output URLs/cause in `download_file`, FlowKit error payloads in [`FlowKitClient._json`](../../apps/backend/src/viraldy/modules/smart_remake/engine/flowkit_client.py#L49), FFmpeg stderr, and model response excerpts in [`parse_llm_json`](../../apps/backend/src/viraldy/modules/smart_remake/engine/gemini_client.py#L74). There is no evidence here that a real secret was exposed; these are unsanitized channels that can carry sensitive content or signed URLs.

**Acceptance:** public errors use allowlisted safe fields, request IDs, and actionable codes; internal diagnostic excerpts/paths/URLs are redacted before logging or returning; tests with synthetic secrets and signed URLs verify redaction. Credentials remain server-side and are never included in trace downloads.

### SR-08 — P1/P2: Resource budgets and disclosure need explicit end-to-end contracts

Repair idempotency and the operation cap are useful, but do not cap new-project initial renders or compile calls. Full upload reads happen before media size validation, and provider outputs are buffered. Model/provider timeouts do not constitute workspace spending controls. No mandatory AI-content disclosure field is bound to generated exports.

**Acceptance:** per-workspace limits cover analysis, initial render, and repair; request/response byte limits are enforced while streaming; cost estimates and actual task spend can be reconciled; quota exhaustion is visible without duplicate paid retries. Export manifests record synthetic origin and required disclosure, and the release gate verifies the selected disclosure policy for the target channel. Exact channel/legal policy is a product input to be defined, not inferred by this audit.

## 5. Rights-related features elsewhere: reuse without overclaiming

- The UGC [`RightsReadinessDrawer`](../../apps/web/src/features/ugc-review/components/rights-readiness-drawer.tsx#L13) presents organic/paid/editing/creator-confirmed/expiry inputs and disabled readiness actions. It imports [`sparkBlockers`](../../apps/web/src/features/ugc-review/lib/mockUgcAnalysis.ts#L91), a UI helper checking field presence. - [`RepairService.accept`](../../apps/backend/src/viraldy/modules/smart_remake/repair_service.py#L641), server-selected storage, content hashes, revision checks, and durable operation records are sensible foundations for an approval/release implementation. Keep technical-check status distinct from rights/content approval.
